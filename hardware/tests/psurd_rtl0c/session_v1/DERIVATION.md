# RTL-0C session package: frozen host timing and P7 budget (plan R2, R3)

Generated by `hardware/tests/psurd_rtl0c/c5_session.py`. 95 steps, 10 distinct expected records.

## Host timing (R2)

| Setting | Value | Derivation |
|---|---|---|
| Serial | 115,200 baud, 8N1, no flow control | `psurd_sys_top` defaults: 25 MHz / 115,200 = 217 cycles per bit |
| Delay between opening the port and the first byte | 0.5 s | The board releases reset 255 cycles of 50 MHz (5.1 us) after KEY0 or configuration; 0.5 s is for the operator and USB, and stale input is drained first |
| Per-response timeout | 1.0 s | The longest response (RESULT, 220 bytes at 11 bit-times) takes 21.0 ms; the device's own inter-byte timeout answers within 0.7 ms. 1.0 s leaves room for USB and host scheduling |
| STATUS polling interval | 0.02 s | One poll exchange is 20 bytes, about 1.9 ms on the wire |
| Maximum polls per wait | 3000 | 60 s at the interval above; the longest run in this session is 2.04 s |

A missing or malformed response is a failure of that step. Nothing is retried.

## P7 budget (R3)

- Commands sent during the long run: STATUS, START, LOAD_BEGIN, RESULT, STATUS. Host bytes and device bytes
  per exchange: [(6, 14), (10, 7), (18, 7), (6, 7), (6, 14)]. On the wire at 115,200 baud (10 bit-times per host byte, 11 per device byte):
  **8.67 ms**.
- Host allowance: 0.1 s per exchange for USB and scheduling latency (an assumption; not measured) x 5 = 0.5 s.
- Safety factor 4: required run time **2.035 s**.
- Cycles per `BR AL 0` iteration: **3**, measured on the RTL core simulation (budgets 1,000 and 5,000 took 3002 and 15002 cycles).
- Budget = ceil(2.035 s x 25,000,000 / 3), rounded up to a million: **17,000,000** retired instructions.
- **Instructions are not clock cycles.** 17,000,000 retired `BR AL 0` instructions x 3 cycles each =
  51,000,000 cycles of the 25 MHz clock = **2.04 s**. (At one cycle per instruction it would be 0.68 s.)
- **Margin if the host is slower than assumed.** The five exchanges must finish inside the 2.04 s run. With
  8.67 ms on the wire, the host may spend up to **0.406 s per exchange** (4.1 times the
  0.1 s allowance) before the last STATUS would fall after the end of the run.

## Sent during the run versus processed during the run

A BUSY answer shows that the command was processed while a run was in flight; the session does not rely on
that alone. The three BUSY commands (START, LOAD_BEGIN, RESULT) are bracketed by two STATUS commands whose
expected payload is flags `01` (image valid, no record), state `01` RUNNING, cause `FF`, and this run's id.
Because the link is stop-and-wait and the device answers in order, both STATUS answers reporting RUNNING
establish that everything between them was received and answered during the run. If the run ended early, the
second STATUS reports READY and that step fails; the BUSY answers are never assumed.

## Stop at the first failure; no retries

`tools/psurd_uart_host.py session` ends at the first step whose response is missing, malformed or different
from the expectation, and sends nothing afterwards. Every byte sent and received up to that point is already
in `traffic.jsonl` (flushed per write) and the per-step outcome is in `summary.json`. No LOAD, START or RESULT
is ever repeated after a timeout: the protocol has no sequence number, so a retry could act twice. This
behaviour is covered by the host-client tests (four link faults, each with exactly one frame sent; a failing
step followed by no further frames).
