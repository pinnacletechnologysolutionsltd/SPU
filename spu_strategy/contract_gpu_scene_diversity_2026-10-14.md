## 1. Objective and Scope

Determine which spatial distinctions the GPU-SOM-0A tile feature schema retains
or discards on a small, deliberately varied T1d scene suite. Establish a
task-sensitive collision oracle before any SOM training, codebook evaluation,
or renderer feedback is considered.

This study operates on the existing software references only. It does not
modify GPU-SOM-0A, its frozen fixtures or evidence, GPU RTL, Soul, SOM models,
symmetry code, or hardware. It does not claim scene generalization from the
small fixture suite.

Target additions after review:

- `examples/gpu/scene_diversity/` — frozen valid scene inputs and a suite manifest.
- `fixtures/gpu_scene_diversity_reference.json` — independent per-pixel oracle
  expectations and collision-pair declarations.
- `fixtures/gpu_scene_diversity_source_lock.json` — frozen source hashes checked
  before and after evaluation.
- `software/spu_gpu_eval/scene_diversity.py` — deterministic suite evaluation
  and collision analysis, separate from observer extraction/publication.
- `software/spu_gpu_eval/scene_diversity_artifacts.py` — source/fixture

- `software/spu_gpu_eval/scene_diversity_publish.py` — no-replace atomic output

## 2. Supported Scene Domain

Use the existing `spu_gpu_scene_v1` parser and `t1d-two-triangle-v1` profile:

- 640×480 pixels and exactly two nondegenerate triangles.
- Integer vertex coordinates, `0..639` by `0..479`.
- Integer depth values `0..65535`.
- RGB444 channels `0..15`.
- Existing packet encoding, finite-width device model, and `device-preview`
  behavior remain authoritative for device-observation features.
- Background color is fixed by the current profile/model. The study must not
  claim background variation support or change the model to introduce it.

The scene suite must include controlled cases for:

1. Disjoint coverage and partial overlap.
2. Both depth-winner orders in overlap and an equal-depth tie.
3. Distinct primitive colors and a shared-color control.
4. Geometry translated within one 16×16 tile while preserving its per-tile
   aggregate statistics.
5. A task-sensitive collision pair whose complete GPU-SOM-0A feature documents
   are byte-identical while their per-pixel primitive/winner maps differ.

The collision pair is a required fixture, not an assumed result. If valid
scenes cannot satisfy the exact collision conditions under the finite-width
device model and independent oracle, halt and report the obstruction; do not
weaken equality to approximate matching or manufacture a collision by changing
the observer schema.

For each required collision fixture, document before evaluation why its
construction is expected to preserve the observed aggregate fields. For
example, translating the same integer triangle by an integer offset wholly
within one tile preserves its shape and pixel count; assigning one constant
depth to its vertices preserves its intended depth range; unchanged color
preserves its RGB histogram. The fixture record must identify these invariants
and the translation. This analytical rationale is a precondition; exact
finite-width feature equality and ideal-oracle pixel differences are still
verified independently. If the finite-width device model violates the expected
invariants, stop rather than altering observer behavior.

## 3. Oracle and Collision Definitions

For every scene, retain two separate outputs:

- **Observed representation:** the exact `tile_features.json` document emitted
  by GPU-SOM-0A from finite-width `device_model.pixel_decision` results.
- **Task oracle:** a complete per-pixel decision map generated by the
  independent ideal `reference.pixel_decision` implementation, including
  coverage, covered primitive IDs, winner, RGB, and exact rational depth data.

Record any device-model versus ideal-oracle disagreement explicitly. Do not
silently treat the device output as an independent oracle, and do not discard a
disagreement from the report. The hand-selected fixture expectations must be
checked against the ideal reference at predeclared sample coordinates and
against device-model observations separately.

For scenes `A` and `B`, define an **observation collision** only when their
canonical feature payloads are byte-identical. The compared payload includes
the feature format/version, tile size, and every serialized tile record with
its coordinates and fields, in canonical order. It excludes the manifest,
scene IDs, source or fixture hashes, run IDs, and all other provenance
metadata. The current `tile_features.json` contains only this feature payload;
do not add scene-specific metadata to it for this study. Define a
**task-relevant collision** when an observation collision also has at least one
pixel where the ideal task-oracle decision differs in coverage, covered
primitive identity, winner, or RGB. Exact rational depth differences alone do
not count as task-output differences in this initial study; this is intentional
because the selected task output is coverage/identity/winner/color. Report the
differing pixel count using only those selected fields and a stable hash of
each complete per-pixel decision map, including exact rational depth for audit.
A collision is harmful for this study only under this explicit task-oracle
definition.

As an optional, non-gating diagnostic, attempt one fixed pair with different
feature payloads but identical ideal visible RGB output. A candidate is the
same geometry and color with the same bounded integer offset added to all
vertex depths in both primitives, preserving relative depth order while
changing reported depth observations. Require byte-identical visible RGB
images under both the ideal oracle and finite-width device model, while the
feature payloads differ. Report it only if all three conditions hold; failure
to construct this optional pair does not fail the study and must not trigger
open-ended fixture search or profile changes.

The required translated-geometry pair must demonstrate that tile aggregation
can discard within-tile spatial arrangement. The required task-relevant pair
must demonstrate a false merge under the selected per-pixel task oracle. A
single scene pair may satisfy both requirements only if it meets both exact
definitions.

## 4. Invariants and Hard Constraints

- [ ] GPU-SOM-0A implementation, frozen inputs, and `_01` / `_02` evidence
  remain unchanged.
- [ ] Every suite scene parses and packet-compiles using existing code; no
  parser, packet, renderer, or device-model behavior is changed to admit a
  fixture.
- [ ] Device-model image output is recorded from the existing finite-width
  path. The observer feature document is produced by the existing observer.
- [ ] Ideal oracle and device-model results are kept distinct, with all
  disagreements reported.
- [ ] Scene IDs, order, expected samples, collision pairs, and serialization
  are frozen and hashed before the evaluator is launched.
- [ ] Feature-document equality is byte equality after existing canonical
  serialization; no ad hoc distance threshold defines a collision.
- [ ] No SOM training, clustering, codebook, learned feedback, D4/E8 transform,
  Soul update, RTL, FPGA, or hardware operation is included.
- [ ] Output publication is atomic. On failure, remove private staging and
  leave a previously absent destination absent; reject existing destinations
  without modification.
- [ ] All claims are limited to the frozen T1d scene suite and task oracle.

## 5. Implementation Instructions

1. Add the frozen scene files and suite manifest under
   `examples/gpu/scene_diversity/`. Use only the supported scene domain in §2.
2. Construct the translated-geometry and task-relevant collision fixtures.
   Record each fixture's analytical invariants and transform, independently
   calculate its ideal pixel map, verify exact feature-payload equality for
   each declared pair, and freeze the fixture expectations and hashes. If
   either required collision cannot be established, stop before evaluation.
3. Add `scene_diversity.py` to evaluate each suite scene using the existing
   parser, packet compiler, device preview/observer, and independent ideal
   reference. Do not duplicate or alter GPU-SOM-0A feature extraction.
4. Add `scene_diversity_artifacts.py` for frozen-hash checks and result
   assembly. Add `scene_diversity_publish.py` for atomic staging/publication.
   Keep each module within the repository's 50–150-line lithic design rule.
5. Emit per-scene hashes, feature counts, oracle/device disagreements,
   collision-pair equality, differing pixel counts, and reference-map hashes.
   Reject missing, duplicate, or invalid pixel coordinates and any incomplete
   scene result.
   Report the optional same-RGB/different-feature diagnostic only if its
   predeclared candidate passes both oracle checks.
6. Add a suite evaluator command:

   ```bash
   python3 -m software.spu_gpu_eval.cli scene-diversity --suite examples/gpu/scene_diversity/manifest.json --out build/gpu_evaluation/scene_diversity_01
   ```

7. Add focused tests for scene validity, the named diversity cases, independent
   sample expectations, complete coordinate coverage, exact observation
   collisions, task-relevant per-pixel differences, deterministic replay, hash
   stability, and refusal/cleanup for output publication failures.
8. Document the frozen suite, measured collisions, device/oracle discrepancies,
   commands, hashes, and the limited interpretation in
   `docs/gpu_scene_diversity_2026-10-14.md`.

## 7. Stop Conditions

- Halt if the two collision fixtures cannot be constructed under the existing
  schema and finite-width device behavior.
- Halt if independent ideal references disagree with frozen point expectations
  or if the implementation conceals device/oracle disagreement.
- Halt if evaluator output depends on SOM state or changes any GPU-SOM-0A
  artifact or renderer decision.
- Halt on incomplete maps, duplicate coordinates, unstable serialization, hash
  mismatch, or non-atomic publication.
- Do not begin GPU-SOM-0B, train a SOM, or add symmetry/Soul/hardware behavior
  without a new reviewed contract.
