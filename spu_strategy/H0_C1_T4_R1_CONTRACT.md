## 1. Scope and edge convention

One clock and one authorized test host; all inputs are stable before the rising edge; each listed trace row is the input at an edge and the required state after it. Synthetic reset is synchronous. There is no SPI framing, real core, ISA decode, physical reset, A31 arithmetic, FPGA build, timing claim or production-width choice. Host commands are synthetic test events. The controller owns admission, interlock, record publication and authorization; the fake engine and fake configuration sink own their storage and MUST obey the commit gates below. The harness owns reset, stimulus, expected traces and test-only epoch tags. The controller does not itself execute engine/sink writes.

Synthetic status comprises lifecycle `CONFIG` or `READY`, progress `p=0,1,2`, a STAGED bit `s`, active transaction identity or NONE, transaction record `(gen,id,state,outcome,result_valid,payload)`, rejection record `(gen,kind)`, configuration-ack record `(gen,kind)`, separate unread and sticky overrun bits, sticky protocol fault `F`, and fake storage `(pair,single,effect_counter)`. `—` denotes absent/invalid; a prior payload may physically remain but `result_valid=0` makes it historical. At reset records are NONE, generations zero, unread/overrun false, F=0, lifecycle CONFIG, p=s=0, no active work; existing committed fake storage and effect counter remain unchanged. Each trace states the initial fake storage and counter. A successful new transaction replaces its record at acceptance and retains the same record generation through completion.

## 2. Two effect owners and commit/cancel boundary

Each fake engine or sink request is PENDING only after one acceptance acknowledgement by that fake unit. PENDING contains a stable identity and payload and has not mutated committed storage. The fake unit may offer a commit intent on a later edge; it can mutate storage once, atomically with a controller grant for that same still-authorized pending identity. That edge is COMMITTED. COMMITTED storage is not rolled back by later invalidation/reset; it cannot count toward a new configuration sequence until freshly re-established and acknowledged. An invalidated pending operation becomes CANCELLED; neither its later intent nor its later ack may mutate storage or advance records. Cancellation, authorization and gates are obligations on the fake sink/engine and controller together: this experiment assumes those fakes obey them; it does not establish a real hardware sink has them.

At one edge the priority is: (1) reset cancels pending work, rejects all same-edge commits and invalidates records/configuration; (2) otherwise a failed configuration submission invalidates configuration and cancels pending sink work before its same-edge commit intent can be granted; (3) otherwise valid owned events and commits are processed; (4) new acceptance is determined from pre-edge READY/busy and an independent rejection may be recorded; (5) snapshots capture pre-edge state. A commit from an earlier edge remains. Existing operation completion plus a new instruction sees pre-edge busy and yields a BUSY rejection while completion proceeds. No configuration acceptance is permitted with an instruction active. One configuration sink operation may be pending at a time. The controller must not authorize an old HIGH commit after invalidation/reset, including after a fresh LOW; the sink checks its matching LOW stage identity and authorization.

Fake engine storage is a monotonically increasing test-only effect counter. Engine commit requires both a matching pending transaction and the controller's grant; it increments exactly once. Once committed, a duplicate intent has no grant, sets F, and cannot increment again. An engine operation still pending at reset is cancelled and cannot later increment; a previously committed effect remains even if reset cancels its unreported terminal. The experiment observes storage directly, not just events. A wrong/old event after reset sets F and has no effect; reset-edge events are cancelled without fault because reset dominates. F is sticky and blocks new issue/configuration until reset. These are prototype semantics, not claims that the real engine can roll back an instruction.

## 3. Configuration

Synthetic manifest is exactly LOW=`12`, HIGH=`34`, SINGLE=`56` in that order (hex). LOW acceptance creates a PENDING sink stage; a granted stage-commit acknowledgement stores stage `(attempt,12)` and produces one STAGED record with p=0,s=1. HIGH acceptance requires that stage; its granted commit atomically writes fake pair `1234`, clears stage, produces COMMITTED and sets p=1. SINGLE granted commit writes `56`, produces COMMITTED and sets p=2, READY. Acceptance alone is not an acknowledgement. The synthetic sink can commit on the first following edge when explicitly driven with matching commit intent; no autonomous hidden writes occur.

Once a sequence starts, any failed configuration submission (bad frame, wrong order/value/target, duplicate, not-ready or busy) records a rejection, cancels pending sink work and invalidates authorization, s and progress; replay the entire manifest. Already committed fake pair/single remains but cannot satisfy the new attempt. An interrupted status read is not a submission and does not invalidate configuration; a host that did not observe an acknowledgement treats it as UNKNOWN and invokes known-reset recovery.

## 4. Transaction and request events

Input `I(kind)` is a valid assertion with immutable kind and payload while high; one assertion is one request and a new request requires a sampled low edge. Repeated identical high is ignored, not replayed. A changed payload/kind while valid remains high is a protocol violation: set F, no new accept/reject/issue. Normal requests use one-edge highs with a sampled low between assertions.

At admission, CONFIG yields NOT_READY before BUSY is considered. READY with an active transaction yields BUSY. An accepted UNSUPPORTED records one terminal UNSUPPORTED immediately, no engine issue/effect/payload. Accepted `OK`, `DELAY`, `REFUSE` are issued once to the fake engine and remain active until completion. At issue acknowledgement edge `t`, the deterministic default engine emits for OK: commit intent at `t+2`, terminal SUCCESS with payload `5A` at `t+3`; for DELAY: terminal SUCCESS `3C` at `t+2`, commit intent at `t+5`; for REFUSE: terminal REFUSED without payload/effect at `t+3`. No SUCCESS publication before both matching commit and terminal. REFUSED/UNSUPPORTED publishes no fresh result or effect. Fault injection can override default timing and duplicate or misattribute events, as explicitly frozen in companion traces.

The test harness must directly inject stale/duplicate intent and stale/duplicate event separately. A rejected event cannot itself undo a prior commit. A sticky protocol fault requires reset recovery; a normal test that deliberately injects a bad event MUST expect F=1 explicitly, while all others expect F=0.

## 5. Epoch, identity, record freshness

The trusted harness provides an 8-bit epoch token E, beginning 1, changing to a previously unused value after each known synthetic reset; every fake event is tagged with its issue-time E. Bound every experiment to at most 200 resets. Controller decisions are correct only given faithful, non-reused tags and unit commit-gate obligations. An old event intentionally mislabeled with the exact current `(E,txid)` and otherwise indistinguishable is observationally indistinguishable from a valid event; the controller is NOT required to detect it. The trace marks this as an assumption-limit demonstration, not a proof of stale rejection. Detection of unknown physical resets remains HOLD.

Transaction identity and record generation are separate. The controller allocates a synthetic 8-bit transaction id monotonically from 1 per epoch, never reused within an epoch; the harness checks the assigned identity and tags fake events with it; limit to 200 admissions per epoch. Configuration request and attempt IDs follow the same bounded non-reuse rule. These test-only tags are not proposed physical identity widths or a claimed cross-reset mechanism. Within one epoch an old txid never matches a new request; events with old epoch or inactive/wrong id cause F without mutation.

Transaction, rejection and configuration-ack records each use independent 2-bit generations, initially 0 and incremented modulo 4 on creation of each new record. The first event has generation 1. Transaction completion updates its accepted record without increment. A record event creates an unread record; a replacement while unread sets its sticky overrun. Transaction acceptance makes EXECUTING unread; terminal update of the *same* identity does not count as replacement; acknowledgement of EXECUTING is forbidden. A second transaction acceptance after a completed unacknowledged one sets transaction overrun. Rejection and cfg-ack records follow their own channels. Overrun forces the host to treat the result as UNKNOWN and recover; ordinary ack cannot clear it. For the adversarial wrap trace, the prototype continues recording incoming rejections while overrun is sticky; this is a synthetic diagnostic behavior, not permission for a compliant host to continue. Reset clears all.

A snapshot captures pre-edge state. Each valid snapshot returns a fresh harness-visible one-shot capability `cap` (synthetic monotonic 16-bit; fewer than 200 snapshots per epoch, never reused). For each channel the controller keeps at most the two most recent unconsumed snapshot capabilities and their captured record serials; a third evicts the oldest. An acknowledgement consumes only the named channel capability. The controller stores cap plus each captured record's internal serial; the serial is a distinct synthetic 16-bit monotonically increasing replacement number, at most 200 events per channel per epoch. A later record replacement invalidates the captured capability for that channel, even if its 2-bit generation wraps to the same value. A transaction terminal state update likewise invalidates any capability that captured its earlier EXECUTING state. ACK(channel,cap) clears unread only if the cap was valid and unconsumed for that channel, the current record serial still matches, no overrun is set, and for transactions the record is terminal. Otherwise ACK is inert; stale/used cap cannot clear anything. Snapshot interruption invalidates its response/cap and does not change other state. Simultaneous snapshot/record update captures pre-edge values but replacement invalidates the just-captured capability for the updated channel. This is bounded synthetic machinery, not an instruction to add wide production counters. Host normally observes and acknowledges each event before submitting the next. Any overrun/ambiguous observation/timeout requires known-reset recovery.

## 6. Verification and negative controls

Companion frozen traces define all inputs and all required selected state after each edge from explicit initial state; omitted fake events are absent. The independent expectation source is the companion file, written before any controller, not generated by the design under test. Verify full specified state, storage, grants and event counts at every row; undefined historical payload bits must not be compared as valid output. Each intentional violation lists expected F and reset clearing. No test is satisfied solely by an unexercised assertion: report assertion hit counts and require each named stimulus/condition to occur.

The frozen negative controls each specify one deliberately defective mutation and the precise trace/edge/assertion it must fail. A detected mutation must compile, run and fail that designated falsifiable assertion; timeout, compile failure or unrelated assertion is not a detection. In addition inject an otherwise matching child process output with nonzero status: the outer runner must fail. Normal suite PASS requires each explicit expected trace (including expected faults), all designated mutations detected, runner control detected, nonzero/error statuses correctly handled, and trace/tool/source identity recorded. Otherwise FAIL. A finite PASS makes no claim beyond these synthetic assumptions.
