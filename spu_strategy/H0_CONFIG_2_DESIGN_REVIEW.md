# H0-CONFIG-2 design review (author's re-examination; NOT independent)

**Independence disclosure.** The reviewed artifact, `spu_strategy/H0_CONFIG_2_DESIGN.md`, was written by the same agent that produced this review. This is a source-verified re-examination by the author, not an independent review, and should be followed by a review from a different agent before any implementation decision. Read-only: no RTL, simulation, edits to R8, T5 or the H0-CONFIG-1 manifests. Source baseline `0f631e37caeabb629b81b84a782cee1d881ac0b9` (isolated checkout `~/.local/gate/spu-config1-0f631e3`).

**Recommendation: REVISE.** The architecture (controller-owned staging with atomic LOW+HIGH replay, authorization separate from physical storage, bundle-based commit evidence) holds up against the source. Four corrections are required first (§1). After them the design is ready for a separately authorized **isolated implementation experiment** (adapter plus stubs, not production integration).

## 1. Required corrections

**C1 — contradiction with R8 on progress.** The design defines `p` as entries committed (0…34, READY at 34) and also says a LOW write must not advance progress. R8 counts steps with a pair as one (`p=1` after the committed pair). The real manifest is 10 Padé pairs plus 14 BTU halves = **24 committed steps**. Define `p` as committed steps (READY at 24) and keep a separate ordering pointer `n` over the 34 entries, or state the adapter mapping. CF-01 and §3 must change accordingly.

**C2 — the manifest set is four, not two.** With the supplementary witnesses the frozen set is SET-N0, SET-R0, SET-N-X1, SET-R-X1. Shared-prefix matching must be a trie over all four, with these stated requirements: no manifest is a prefix of another; identity is *provisional* until the divergent entry is COMMITTED (not merely staged or accepted); a failure, reset or mismatch returns to "unselected"; identity cannot change after selection without a full new attempt. Divergence points: N0/R0 at entry 10; N0 or R0 versus the X1 pair at entry 2.

**C3 — undefined failure of the commit evidence.** The design says an entry is COMMITTED when the bundle matches, but not what happens when the bundle differs from the entry, never appears, or appears without a grant. Required: a mismatch or a timeout fails the attempt (new kind, e.g. `COMMIT_MISMATCH`), invalidates authorization and replays; any bundle write-enable not caused by a controller grant sets the sticky fault (the SPI path is the only legitimate source and is disconnected by the integration). Also, a Padé HIGH is compared against the **pair** (stage register ‖ HIGH entry), not against the HIGH entry alone as §5 could be read.

**C4 — verification gaps.** (a) No case resets or interrupts between the two replay pulses or between the HIGH pulse and the bundle compare; CF-03 resets between *frames*. Add: reset between pulses; reset after the HIGH pulse before the comparison; reset on the last entry before READY is visible; bundle mismatch; missing bundle. (b) M-C1 (LOW forwarded to the core immediately) is not detected by CF-05, because the controller still rejects an unpaired HIGH. It needs an assertion that **no core configuration pulse is produced at LOW acceptance** (add to CF-03/04/15). (c) M-C7 needs a checker independent of the controller comparing the bundle with the manifest. (d) CF-16 should be replaced by a structural assertion plus an assumption monitor (see §2). (e) Add manifest-selection cases: divergence at entries 2 and 10, wrong value after selection, stop at entry 9 then reset, and a supplementary-versus-baseline switch after failure.

## 2. Findings that hold (source-verified)

**Replay timing.** In the Artix top the SPI slave and the core are both clocked by `clk_fast` (`u_spi .clk(clk_fast)`, `u_core .clk(clk_fast)`), so the configuration pulse needs no clock-domain crossing. `sck_rise` is the pattern `01` in a 3-stage sample history of SCK, so two detected rises are at least two `clk_fast` cycles apart. A configuration pulse is emitted only after a full frame of 8 (command) + 64 + 64 + 8 (CRC) = 144 detected rises. Hence consecutive configuration pulses are **at least 288 `clk_fast` cycles apart whatever the SCK frequency**, with no assumption about the SCK/`clk_fast` ratio. A replay of a few cycles therefore cannot overlap a following configuration frame, and no frame buffering is needed; a defensive "pulse during replay" fault should still be asserted. (`0xB1` frames need 80 rises ≥ 160 cycles.)

**Consecutive write cycles.** The core decodes `dec_fast_cfg_*` combinationally. The staging array is written inside the final `else` of the core's sequential configuration block (preceded only by reset and the boot-time `prime_we` branch, with `prime_we` tied to 0 in the Artix top), so one configuration write is accepted per cycle. A LOW pulse at cycle *k* updates the staging array at the end of *k*; the HIGH decode at *k+1* reads the updated value combinationally, and the engine array is written at the end of *k+1*. This is derived from source and not simulated; it remains an assumption to verify.

**Staging versus architectural commitment.** The replayed LOW mutates only the core staging array, which is not read by the evaluator; the architectural commitment is the HIGH write into the engine array (`coeff_we`). A reset or interruption between the two pulses can leave the staging array updated but the engine array unchanged; since the next attempt overwrites staging before each HIGH, this is safe. A reset after the HIGH pulse leaves a physically changed engine entry that cannot authorize (R8: COMMITTED is not rolled back).

**Commit evidence.** The Padé bundle is the engine's own input pins and the BRAM write pins are the BTU's input pins. The engine array and BRAM bodies are unconditional clocked writes with no reset or gating, so an observed bundle implies the write at the next edge. This is **not** independent readback: it does not detect synthesis-level misbehaviour or a faulty memory, so the stated assurance is "write issued with intended data", adequate for bring-up only together with the mathematical witnesses. The standalone engine testbench `rplu_thimble_pade_tb.v` loads vectors with nonconstant numerator and denominator coefficients, which supports the engine arithmetic for X1 in isolation; end-to-end coverage through SOM, BTU and configuration is not yet evidenced.

**H0-C1/R8 compatibility.** The extensions (`CONFIG_BUSY`, authorization revoked at the first accepted frame of a new attempt, definitions for configuration while READY or active) are production extensions and must be labelled so; R8 is not modified. Real replay needs adapter state absent from R8's fakes: a stage register, a replay FSM (idle/LOW/HIGH/compare), a compare timeout, and the non-cancellable rule that reconciles R8's "mutation atomic with the grant" with a two-cycle replay.

**Witnesses.** SET-N-X1 and SET-R-X1 were recomputed with two methods (`a31_field.py`; an independent multiplication table with Gaussian-elimination inversion). The coefficients, row selection (lane (2,0,0,0) → node 1 → row 1) and exact M31 arithmetic are as stated; all coefficients and row limbs are canonical (< 2³¹−1), so no finite-width effect arises; the standalone engine's Horner covers degree 4. The incomplete-configuration variants are meaningful, but they assume omitted destinations keep SET-N0 values; the witness should be run after a different prior manifest (for example SET-N0 then SET-N-X1, and SET-R0 then SET-N-X1) so a stale value is also exercised.

## 3. Remaining assumptions

Two-pulse replay and one-write-per-cycle behaviour are unsimulated; the 288-cycle bound depends on the 3-stage synchronizer as written; hardware power-up values of the arrays and BRAM are unknown (the full-manifest replay removes the dependence only for manifest-covered state); kappa remains unresolved; production widths, manifest storage and the SPI-slave header tap are undecided; the bundle is an input-pin observation, not readback.

## 4. Readiness

Ready for a separately authorized isolated implementation experiment after C1–C4 are incorporated in the design document, with scope limited to the configuration adapter, a stub core exposing the bundle, and a testbench driving the corrected CF matrix and mutation controls. Not ready for production integration.
