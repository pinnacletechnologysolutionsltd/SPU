# H0-C1-T2 — Transaction interface contract closure proposal

**Disposition: REVISE.** This is a documentation-only, non-normative proposed interface contract for independent review, not RTL implementation readiness, hardware evidence, a frozen protocol, or authorization to implement. The interface can be made precise, but the reset-observability and paired-write acknowledgement conflicts in §7 and §8 need an owner decision; D2, D7, D10–D16 and canonical masks have outstanding dependencies. NUM-SOM-4 Phase B and production implementation remain HOLD.

H0-C1 r6 and H0-NUM-1 r5 in that tree are the governing drafts. The untracked T1 review is background, not part of this baseline. ## 1. Baseline facts and target boundary

**Observed:** the synchronized SPI slave emits a registered one-cycle `inst_valid` after B1 CRC succeeds; no `inst_done` return port is connected to it (`hardware/rtl/peripherals/io/spu_spi_slave.v:875–896`). In the Artix-7 top, sidecar claims filter core ingress, and an OR of core done and sidecar commits exists (`hardware/boards/artix7/spu_a7_top.v:427–430`); this OR is not a transaction record. Core acceptance depends on boot/valid, `inst_seen` and `surd_busy`, not a whole-engine interlock (`hardware/rtl/core/spu13/spu13_core.v:693–710, 731–736`). QLDI/QSUB register a write request, telemetry and `inst_done`; the QR file samples the registered write on a later edge (`spu13_core.v:1360–1392`, `hardware/rtl/core/shared/spu_quadray_regfile.v:51–73`). RPLU2 result-valid directly drives telemetry and done (`spu13_core.v:1328–1340, 2310–2314`), and SPI's `0xAE` latch stores the last commit without per-transaction freshness (`spu_spi_slave.v:405–412`). None proves a complete H0 transaction or physical timing.

**PROPOSED:** exactly one transaction owner at the Artix-7 dispatch boundary, after transport frame verification but before *any* protected instruction or configuration initiation. The parser delivers events to the owner; the owner owns authorization, transaction/rejection records, configuration lifecycle and snapshot. The engine owns execution, actual effect-commit and terminal evidence. The host owns serialized submission, polling and recovery. Excluded sidecars and autonomous masters receive no request and cannot independently mutate protected state.

```text
SPI pins -> synchronized parser -> frame / rejection event -> transaction owner
                                                          | instruction / config authorization
                                                          v
                                                   qualified H0 core
                                                          | commit, terminal, payload, reason
                                                          v
                         coherent snapshot <- owner records + lifecycle + configuration progress
                          additive read                success-only legacy 0xAE
```

No command value, wire encoding, register layout, counter width or new instruction is assigned by this proposal. Common-clock owner/engine events use `clk_fast`; asynchronous SPI inputs and any other CDC remain independently qualified as in §8.

## 2. Proposed semantic signal contract

Signal names below denote interfaces and ownership, not existing RTL ports or required implementation spelling. Each receiver must capture the event on the specified clock; a pulse is acceptable only where a continuously ready same-clock capture is proven. Cross-domain or stallable paths require held data with acknowledgement or equivalent lossless transfer.

| Interface | Producer → consumer | PROPOSED contract |
|---|---|---|
| `frame_event(class, word/header, payload, transport_status)` | parser → owner | Exactly one event for each complete B1/A5 or recognized CRC/malformed/abort; full bits stable on capture, one event per frame. Header includes selector, material, address and subfields. Unrecognized fragments generate no event under r6. Events for 0xAC/0xAE preserve their existing behavior. |
| `accept(id, authorized, word)` / `reject(rej_id, kind, class)` | owner → engine / host record | Evaluate readiness and pre-edge busy once. READY/idle complete B1 acquires a new identity even if canonical check fails; unsupported finishes without dispatch/effect. Busy/not-ready is a rejection and gets no transaction identity. Capture word and authorization once. Rejection does not inhibit an in-flight transaction. |
| `issue(id, word, authorization)` + `issue_accept(id)` | owner → engine; engine → owner | One issue for a valid supported transaction. Engine acknowledgement means ownership has actually transferred, not merely `inst_valid` presented. Owner retains word/identity until accepted; a level held valid is consumed once. This acknowledgement is absent at baseline. |
| `effect_commit(id, lane, effect)` | engine → owner | Transaction-associated event only once the specified QR architectural write and tags have actually taken effect. Not equivalent to request, write-enable or `inst_done`. For telemetry-only RPLU2, no QR write event is required; successful telemetry capture is the relevant publication prerequisite. |
| `terminal(id, outcome, reason, result_valid, lane, payload)` | engine → owner | Exactly one terminal per accepted authorized transaction, with identity and payload stable for capture. REFUSED and UNSUPPORTED have `result_valid=0`, no fresh payload/effects. SUCCESS names only the transaction's successful payload; numerical refusal is REFUSED/NUMERIC_DOMAIN. `inst_done` by itself is neither outcome nor effect commit. |
| `config_accept(entry)` / `config_stage_ack(entry)` / `config_commit_ack(entry,pair)` | owner ↔ configuration engine | Entry is complete selector/material/address/subfield/value with manifest position and set identity. Stage acknowledgement means a low half was captured only; commit acknowledgement means target state was actually updated. No input rewrite can be called committed merely because a request was accepted. |
| `snapshot_request` / `snapshot(records,lifecycle,progress)` | parser ↔ owner | One atomic non-destructive pre-edge capture of both records, active set identity and configuration status; response is stable while serialized. Snapshot is not a command encoding or a promise that 0xAE itself has become fresh. |
| `cancel/reset` | synchronized reset → all | Highest priority; cancels in-flight ownership and staged halves, invalidates configuration and records, and suppresses every post-reset event from the old transaction. |

**PROPOSED timing interface:** terminal may arrive before or after a QR `effect_commit`; owner must remember it and publish only after both are present for the same identity. Where same edge gives both, publish after that edge has effected the write; a subsequent instruction is not admitted until post-commit publication. For `0x2A`, publish success only after the valid payload is durably captured and associated with the identity; no QR write is inferred. A refusal event such as future `rplu2_domain_refused` is captured with the matching outstanding identity and cannot be classified as success; a one-cycle internal signal is safe only under the capture conditions above. The eventual exact commit timing and refusal-port wiring remain unverified.

A malformed engine combination (two outcomes, conflicting identities, early payload, or late result after terminal) must never be published as SUCCESS. **UNRESOLVED D7:** its terminal outcome and recovery are not defined; use conditional liveness rather than inventing an error class. A prior success retained in `0xAE` remains historical and is never treated as a valid result of a later refusal or unsupported transaction.

## 3. Instruction state, admission and ordering

**PROPOSED** logical state is `RESET → INITIALIZING → CONFIG_REQUIRED → CONFIG_VALID → READY_IDLE → OWNED → WAIT_COMMIT → PUBLISHED → READY_IDLE`; `OWNED`/`WAIT_COMMIT` are one outstanding interval even if a design uses different encodings. A completed transaction record remains stable until next acceptance or reset; rejection record is independent. The owner must reserve the source lane and transaction association for the full interval, prevent any second issue, and block configuration mutation while outstanding. The full source data for RPLU2 remains stable from guard through pipeline capture. No pipeline result from an earlier operation may be mistaken for this operation.

At admission the **PROPOSED** classifier checks opcode, enabled profile, canonical lane fields 0–12, reserved-zero fields and ROTC angles `{0,2,5}`. The proposed per-opcode masks are in H0-NUM-1 r5 §2; their ambiguity is **UNRESOLVED**, not a new frozen encoding. `QLDI 0x1D`, `QSUB 0x1B`, `ROTC 0x1C` and RPLU2 `0x2A` are the only candidate instructions. Supported noncanonical/other opcode words are accepted at READY then terminal UNSUPPORTED without any instruction-owned, configuration-owned or prohibited background effect. B1 CRC failure, not-ready and busy are rejections, not transactions. Unsupported `0x2A` operands must not launch any parallel decoder or set pending state.

On an accepted canonical `0x2A`, the engine must check the eight selected original signed 32-bit coefficients in `[-9457,9457]` after the selected lane is available and before narrowing is used or SOM starts. Failure completes once as REFUSED/NUMERIC_DOMAIN, no SOM/BTU/Padé start, QR mutation, fresh telemetry or late result. The separate A31 validity fix must report its characterized zero-divisor refusal and suppress stale success; neither prerequisite is assumed implemented. QSUB's independent 32-bit modular halves are unchanged.

**PROPOSED event arbitration, r6-aligned:** all predicates use pre-edge state. Reset wins. An interrupted recognized frame is abort; on final-bit/deadman coincidence the sampled final CRC bit wins. B1 evaluates not-ready then busy then accept/classify; A5 evaluates malformed header, unsupported target, initialization-not-ready, busy, sequence violation, then valid write. Completion and a *different* rejection on the same edge update the independent records. A request on a completion edge sees pre-edge outstanding and is rejected busy. Same-edge acceptance/completion is allowed for unsupported or a truly completed operation with the new identity; no imaginary QR commit may be assumed. Snapshot capture sees registered pre-edge records; concurrent updates appear on the next snapshot. Reset interrupting a read invalidates the response; CS drop terminates it with no mutation. Multiple rejection events in a single cycle are **UNRESOLVED** until parser serialization or an explicitly bounded multi-event policy is demonstrated; no rejection may silently disappear.

## 4. Commit, freshness and coherent records

**PROPOSED** owner holds two independent records. Transaction: NONE/executing/completed, reset-scoped identity, outcome/reason, result-valid, payload/lane and associated configuration identity. Rejection: NONE/present, generation, kind and command class. Outcome/reason belongs to the identity; no old 0xAE data may be substituted for a fresh payload. Both record updates and lifecycle/progress are snapshotted coherently before SPI serialization. Completion and rejection are separate events, not competing writes to a single shared record.

For QLDI, QSUB and ROTC, commit means the QR file and associated tag have accepted the intended write; captured telemetry is bound to that effect. Baseline registered enable and telemetry do not alone prove the later write was committed, so a transaction-associated commit event or a demonstrated equivalent is required. For RPLU2 the successful result is telemetry only, with no QR register-file write. `terminal` must carry distinct validity and refusal; `rplu2_domain_refused` and the A31 flag path must be captured and arbitrated independently of any legacy `inst_done`. Existing `0xAC` and `0xAE` command/field meanings and sticky/clear behavior remain; success-only updates to `0xAE` repair the existing A31 stale-valid error, and refusal leaves previous payload historical. Additive coherent record reporting is required; no SPI values or bit layouts are selected here.

## 5. Configuration ownership and manifest verification

**Observed:** Padé numerator/denominator low pairs are staged in the core (`spu13_core.v:1872–1882`); configuration writes can also enable torus emission (`:1866–1870`, `:1967–1974`). The parser exposes decoded fields (`spu_spi_slave.v:884–890`), not a committed-pair acknowledgement. Neither two manifests nor their comparison is established by this source.

**PROPOSED:** reset/config invalidation puts the owner in CONFIG_REQUIRED once hydration finishes; B1 receives not-ready until one SET-N or SET-R has been established. A selected set has immutable image-bound identity and an exact ordered manifest of full `(selector, material, address, subfield, value)` entries and expected underlying paired commits, BTU rows, global Padé arrays, kappa and all other included writable state. Fixed SOM weights belong to build identity, not runtime configuration. Host-declared hashes are insufficient: compare every complete frame's identity and value to the expected entry before staging, and match actual committed target and both halves before advancing committed progress. No unallowlisted write, including torus control or purported SOM training, may mutate or stage. A rejected/malformed write has only its permitted transport diagnostics. Incomplete, stale, duplicate, reordered or wrong values invalidate the attempted sequence and any affected authorization; reset discards staged halves. Switching set, or a covered valid-state rewrite, first invalidates READY and requires a new complete sequence. No writes while an instruction is outstanding.

**UNRESOLVED acknowledgement conflict:** r6 CFG-6 says a low half must not advance committed progress, while CFG-7 requires an acknowledgement *after each write committed*. A low half is not itself a committed four-limb coefficient. Proposed resolution for independent review: host-visible distinct fresh `STAGED` acknowledgement for each accepted low half (identity + expected partner, not committed progress), followed by `COMMITTED` acknowledgement after matching high half has actually updated the complete coefficient and advanced committed progress. Other single-step targets acknowledge their real commit. The precise stage-ack shape, manifest selection, per-entry atomicity and whether this satisfies the approved CFG-7 wording require owner approval; do not silently redefine it. A timeout or sequence failure must not grant configuration-valid status, even if some physical coefficients have been written.

## 6. H0 image and protected partitions

**PROPOSED profile** is the existing r6 candidate only: Artix-7 XC7A100T, host-driven single outstanding, core and math enabled, RPLU2 pipeline enabled, signed-P comparator selected for that pipeline and signed Q; candidate ROTC `{0,2,5}`; QLDI/QSUB/ROTC/RPLU2 `0x2A` only. Owner-approved ±9457 applies only to original coefficients for this fixed SOM configuration. SET-N/SET-R remain unpopulated, unqualified manifests. Full build parameters and source/tool/clock identities must be frozen in an image manifest.

**PROPOSED exclusions:** coreless/live/Padé, Lucas, SU3, Neuro and other sidecars; legacy core SOM, REGEN, IROTC, Surd, JSCR/NSA extension bundle, sequencer, legacy RPLU and GPU/I2S/torus/lattice/SDRAM/gatekeeper and other unlisted peripherals. Distinguish the *internal* SOM/BTU/Padé within RPLU2 from excluded standalone SOM. Preserve the QR hydration/reset and configuration mechanisms needed to reach READY. A listed exclusion is a requirement, not evidence that the baseline gates it.

Protected instruction effects include QR contents/tags and write enables, commit and HEX/debug outputs, ROTC/SOM/BTU/Padé starts and pending flags, Artery writes, REGEN counters, `fpga_chain` inputs/state, result validity and records. Protected configuration effects include staging arrays, Padé coefficients, BTU rows, kappa, torus controls and all addressable state. Autonomous hydration/stability/scale/memory/audio and emitter paths must be either enumerated and permitted with noninterference evidence or disabled; control-word filtering alone is insufficient. **Observed:** `spu_a7_top.v:759–774` does not pass `ENABLE_REGEN`, and `fpga_chain` is instantiated outside its generate guard (`spu13_core.v:1107–1134`); source alone does not prove it absent/inert. `spu13_core.v:1902–1905` has an instruction Artery path and `:1967–1974` has an autonomous torus emitter. The actual included block inventory, gating/elaboration and timing remain **HOLD**.

## 7. Identity, freshness and host recovery

**PROPOSED r6 discipline:** a single host snapshots `(state,id)` for both independent records, submits one frame, then polls until a new transaction identity reaches completed or a new rejection generation appears. No next instruction is sent until the preceding event is observed. Sequence and rejection generations advance on each respective event modulo their documented widths; compare within a single known reset epoch and impose fewer than half the modulus of unobserved events. Width, overflow behavior and exposed overrun are **UNRESOLVED D2/D8**, so this is a behavioral constraint rather than a selected hardware counter. A one-bit alternating tag is not asserted sufficient. No identity is compared across a reset.

**UNRESOLVED reset gap:** r6 treats NONE as reset indication, but an unobserved reset followed by rehydration and new events can overwrite NONE before the host polls; counters can also return to prior values. NONE alone cannot guarantee detection under arbitrary reset/restart traffic. Owner must select either a durable reset/epoch indication, a reliable external reset-observation guarantee with bounded host/traffic assumptions, or an explicit contract limitation and recovery rule. Without that decision, do not claim all reset races are detected. Likewise, latest-only rejection cannot preserve arbitrary unobserved rejections; one host and one submission at a time are assumptions, not protection against unsolicited traffic.

Host timeout is **outcome unknown/recovery required**, not REFUSED or proof of no side effects. Stop submissions, assert the documented physical reset, verify reset availability, rehydrate a complete manifest, and establish fresh record baselines. If reset cannot be asserted or observed, automatic recovery is not guaranteed. Reset cancels outstanding work and invalidates authorization, records, staged halves and progress; no pre-reset terminal/commit may become a post-reset success. A board mechanism and evidence are D16 HOLD.

## 8. Clock, reset and snapshot requirements

**Observed:** top connects core and SPI to `clk_fast` and `rst_n_int` (`spu_a7_top.v:776, 1091`); SPI pins are asynchronous and synchronized by the slave; top reset derives from physical `rst_n` with synchronization/hold (`:153–176`). The core `boot_done` is tied high by the top but READY also depends on hydration (`:785`; `spu13_core.v:654–686`). Static source does not establish legal SCK ratios, pulse observability, phase margin, constraint coverage or board reset access.

**PROPOSED:** owner, effect/terminal capture, configuration acknowledgements, records and snapshot share the qualified engine clock/reset or use explicit lossless CDC. A same-clock one-cycle refusal requires a ready receiver sampling that edge; an asynchronous or stallable receiver requires a synchronized held event/acknowledgement and stable data. Snapshot reads latch the complete pre-edge record set at command decode, hold it unchanged through transmission, and are non-destructive. Reset asserted before/during read cancels/invalidates response; the host discards any interrupted response and resynchronizes. CS drop terminates a read. Actual reset assertion/deassertion implementation, clock release, SPI rate/phase/CS limits and finite qualification operating points remain D12/D16 HOLD; no ratio is assumed.
