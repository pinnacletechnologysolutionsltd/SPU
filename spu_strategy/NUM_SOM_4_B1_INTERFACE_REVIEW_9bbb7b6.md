# NUM-SOM-4-B1 — RPLU2 numeric-domain refusal interface review

**Disposition: REVISE.** A distinct refusal pulse alongside generic completion is a reasonable internal experiment, but reliable capture and attribution are conditional; the current Artix-7 SPI path has no transaction controller or refusal input. A core-only pulse is not H0-C1 host-visible completion. Phase B implementation remains HOLD.

**Identity and scope:** source inspection at `9bbb7b698029ee38728bcc87ce39e82062adc0f8` (`dev/next`); existing unrelated untracked strategy files were not reviewed or changed. No simulation, synthesis or hardware work. Findings below are source-derived, not observed waveforms. H0-C1 remains a non-normative future contract (`docs/isa/H0_C1_PROTOCOL_CONTRACT_DRAFT.md` §§4–7).

## Findings

1. **Major — no existing host or transaction-controller receiver.** `spu13_core.v:1250` drives `inst_done` from `inst_done_r`, a register defaulted low each non-reset clock (`:1318`) and asserted by completion branches. An enabled in-core sequencer consumes it (`:615–627`, `spu_sequencer.v` S_WAIT). Artix-7 connects core `inst_done` to `core_inst_done` (`spu_a7_top.v:799`), records a debug sticky (`:510`), and forms a top-level OR with sidecar commit pulses (`:429–430`). That OR has no further reader in this top, and the SPI slave has no `inst_done` input (`:1091–1118`). SPI `0xB1` instead emits a one-cycle valid strobe after CRC (`spu_spi_slave.v:894–896`), without a completion handshake. Therefore an OR at the top is not a host response or handshake release, and cannot convey a refusal reason. A future controller must explicitly receive the paired event, retain transaction identity and publish its outcome; no such boundary can be verified on this baseline.

2. **Major — distinguish pulse alignment from reliable attribution.** If a registered `rplu2_domain_refused` is high for one complete core clock period and is ORed combinationally into the existing `inst_done` output, a synchronous always-ready receiver on the same clock can sample both high on the next edge, provided reset does not cancel the event and the pulse has one owner. This follows from synchronous nonblocking register semantics, not from a test. A receiver in another clock domain, clock-gated or not ready on that edge can miss it; it needs a captured/held event or a proper CDC handshake. A controller must latch reason with completion and the accepted transaction identity atomically, with refusal taking precedence over success. A pulse alone is not persistent polling evidence. Reset must cancel both event and pending transaction, with no late event. Consecutive or simultaneous events require defined handling; do not infer success from `inst_done` or from absent QR commit.

3. **Major — ORing done is safe only with explicit ownership and exclusivity.** `inst_done_r` is assigned by the main core clocked process, whose priority starts with Surd retire and RPLU2 result (`spu13_core.v:1328–1340`), before other operations. Driving that register from the RPLU2 generate process would create competing procedural drivers. A separate registered refusal event can feed a single continuous `inst_done_r || rplu2_domain_refused` expression, with an explicit zero source when the feature is absent; the public refusal signal must be separately exposed if a non-hierarchical consumer needs it. This preserves the existing register's one owner, but it does not establish that `inst_done_r` is low on the refusal cycle. A coincident old result, Surd retirement, or sidecar event can combine unrelated events or cause a fresh commit; source alone does not prove such collisions unreachable. Prevent or explicitly arbitrate them under a single-outstanding contract. The top's existing sidecar OR loses source identity and cannot by itself provide attribution.

4. **Major — proposed guard point is after lane selection, before pending launch.** At accepted `0x2A`, the main core latches `rote_src_lane` (`spu13_core.v:1586–1592`); the RPLU2 generate block independently sets `rplu2_som_pending` on the same edge (`:2323–2327`). The QR file reads the selected lane asynchronously (`spu_quadray_regfile.v:75–78`), with combinational ECC correction (`spu_quadray_regfile_ecc.v:1–5, 88–98`); after lane selection settles, the four `qrf_rd_*` words expose all eight original halves. The existing low-18-bit extraction is combinational (`spu13_core.v:580–594`); the meaningful requirement is to check the full original values and suppress **launch/use** of narrowed values on failure, not that combinational extraction never toggles. At the next eligible `rplu2_som_pending && !rplu2_busy` edge (`:2323`), check signed 32-bit P/Q of A–D against ±9457; only the passing branch may assert `rplu2_som_start`, while the failing branch clears pending and emits one refusal event. This location assumes the acceptance branch actually selected the lane, no competing write changes it before sampling, and lane/data settle within the clock period. The next edge launches SOM from the registered start; keep the checked lane/data stable through the pipeline's feature capture or explicitly latch the checked data. Timing closure and actual event ordering require later verification. ECC double-error policy remains H0-C1 D7, not automatically NUMERIC_DOMAIN.

5. **Major — one outstanding operation is an assumption, not an existing guard.** `inst_accept` only checks valid, `inst_seen` and `!surd_busy` (`:693–710`); `inst_seen` clears when valid falls (`:731–736`). It does not reserve the shared read lane, result label, or protect the RPLU2 pending/start window against another instruction. The pending launch is in a separate always block from the priority chain that writes the lane; another branch taking priority, a second instruction, outstanding writes, or a previous result can defeat the intended association. Require one accepted instruction at a time from acceptance through terminal event and settled architectural effects, with no other read-lane change, write/hydration of the source, sidecar activity or pre-existing pipeline result. This must be enforced by the test driver in a core-only experiment and by the future H0 controller in the qualified system; it is not established by the present SPI strobe. Also ensure the parallel pending latch cannot fire unless the lane-selection branch belongs to the same accepted transaction.

6. **Minor — ROTC bad-angle precedent has limited scope.** `spu13_core.v:1407–1417` checks angles above `ROTC_MAX_VERIFIED_ANGLE`, sets debug flags `8'b1000_0001`, clears debug busy and sets `inst_done_r` on that edge, without starting rotor or setting QR write/commit in that branch. It demonstrates a generic completion plus fault indication in an isolated execution; `rotc_debug_flags` is persistent debug state, not a transaction-scoped refusal record. Independent always blocks and overlapping events remain outside that branch-level inference. H0's proposed supported-angle policy is narrower and is not identical to this current RTL check.

7. **Major — telemetry and sidecars are separate.** `rplu2_result_valid` directly triggers QR-shaped result telemetry and done in the priority chain (`spu13_core.v:1333–1340`, `:2310–2314`); this is telemetry rather than a QR register write. SPI retains the latest `qr_commit_*` in sticky `qr_valid_lat` (`spu_spi_slave.v:405–412`); a refused operation must not present that old latch as fresh. A31 invalid-result publication remains a separate unresolved repair. Restrict the guard and pulse to the core generate branch `ENABLE_CORE_RPLU_V2 && ENABLE_CORE_RPLU_V2_PIPELINE`; drive the event low outside it. Artix-7 sidecar paths are separate instances and can claim the SPI word before the core (`spu_a7_top.v:427–428, 986–1030`); legacy core SOM is a different generate path. The H0 build and shared classifier must exclude or arbitrate those paths; merely inserting a guard in the core does not establish system-wide coverage.

## Minimum internal interface and tests

For a constrained core experiment, provide an observable one-cycle `rplu2_domain_refused` indication that is registered at the failed guard edge and aligned with the core's generic `inst_done` output; make the signal available to a directed testbench, and to the future transaction owner when integrated. No SPI reason encoding is needed for this internal experiment. The receiver must sample both on the same core clock, be continuously ready, and associate them with the one outstanding accepted operation. If these assumptions cannot be guaranteed, use a held event with acknowledgement or an equivalent durable capture, not an unacknowledged one-cycle crossing. This is a proposed interface, not implemented behavior.

Directed RTL tests should cover: all eight full-width coefficient positions at ±9457 and ±9458, signed extremes and 18-bit aliases; correct selected-lane read and stable source; passing launch exactly once; refusal exactly once with aligned done and event, no SOM/BTU/Padé start, QR write, fresh commit or later output; back-to-back distinct transactions after completion; reset during pending/refusal/launch; and coexistence with a prior sticky `0xAE` result. Include controlled collisions with prior result/Surd/sidecar activity and competing instructions to verify the stated single-outstanding boundary, rather than assuming priority makes them safe. Test disabled/config-only generate branches and legacy SOM/sidecar isolation. Observe `inst_done`, refusal, pending/start, selected QR data, pipeline activity, register writes and telemetry independently. Require simulator exit status zero and expected checks to pass.

**H0-C1 dependencies:** an implemented transaction owner and acceptance/busy policy; coherent durable record with reason, identity and result-valid; reset and CDC/clock-domain behavior; sidecar arbitration; source-data stability; A31 validity/refusal propagation; integrity-fault classification; SPI freshness and actual operating-point/timing qualification. None is proven by this read-only review. Refusal is distinct from an unsupported encoding or transport rejection, and `inst_done` is not success.
