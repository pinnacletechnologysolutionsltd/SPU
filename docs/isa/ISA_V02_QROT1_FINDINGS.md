## Implemented operation

`QROT QRn` (both VMs): `n = R1 mod 13`; each component `x` becomes `x·(2+√3)` by exact `Q(√3)` multiplication, then the common minimum component is subtracted (`normalize`, exact `Q(√3)` ordering). `R2` is ignored (assembler encodes `QROT QRd [, Rs]` into `R2`). The Python VM then sets the φ-plane tag to `PHI_UNTAGGED`; the C++ VM has no tags. A component that carries a Pell tag (from `LD R,1,0` or `ROT`, moved by `QLOAD`) is instead **replaced** by `PELL_ORBIT[(step+1) mod 8]` regardless of its stored value. Sources: `software/spu_vm.py` (`RationalSurd.rotate_phi`, `QuadrayVector.rotate`, `OPCODES["QROT"]` branch), `software/vm/spu_vm.cpp` (`rotate_phi`, `QuadrayVector::rotate`, `case 0x11`), `software/tools/spu13_asm.py` (`QROT` encoding). `ROT` has the same in-place single-step shape and also ignores `Rs`/`n`.

## Results (u = 2+√3)

Proven (bilinearity / multiplicativity): `Q(u·v) = u²·Q(v)`; `B_Q(u·v,u·w) = u²·B_Q(v,w)`; spread `N/D` invariant (both scale by `u⁴`); `N_{Q(√3)/Q}(Q(v))` invariant because `N(u)=1`; the map is `Q(√3)`-scalar multiplication on gauge classes, hence a similarity of ratio `u²` (≈13.93 in the real embedding), a bijection with inverse `×(2−√3)`, **not** an isometry. `rot(v + c·(1,1,1,1)) = rot(v)` literally follows from `normalize(x + t·1) = normalize(x)` for exact minimum subtraction (no ordering or sign assumption on `u` is needed). `rot` is not literally additive: `normalize` subtracts a data-dependent minimum.

Sampled only (310 vectors, 1800 pairs; scenario programs): the above identities in the VMs' actual arithmetic; FIELD-0 witness `(3,1,0,0)`: Q 24 → `(168,96) = 24·(7+4√3)`, matching `test_field0_intrinsic_metric.py`; both VMs agree on every non-overflow scenario.

Pell-tag path (identical in both VMs): steps 0–6 equal `u·value`; `r⁷ = (5042,2911)` → `(1,0)` (mantissa wrap: Q 152530581+88063572√3 → 3, not `u²·Q`); mixed steps scale components differently, so it is not a similarity. The octave count is dropped by `normalize`.

Bounded profile: Python is unbounded. C++ checks `int32`: starting from `(100,0,0,0)`, the 14th `QROT` is refused (atomic restore of regs/QRs/PC/counters, halt, rc 1). For 10–13 rotations all `QROT`s succeed and the process then aborts uncaught (rc 134) in the end-of-run register display.

Incorrect source comments (not edited): `spu_vm.py` (`QuadrayVector.rotate` docstring) and `software/common/include/spu_quadray.h` (header and `pell_rotate`) say quadrance is preserved.

## Recommended normative definition (ratification HOLD)

`QROT QRn` replaces `QR[n]` with `normalize(u·QR[n])`, `u = 2+√3` (a similarity of ratio `u²`; preserves spread, gauge equivalence and the Pell norm of the quadrance; not quadrance). HOLD: the Pell-tag/octave path; bounded-profile refusal and the display-path crash; whether `QROT`/`ROT` keep the historical `Rd, Rs, n` form.

## Questions for the adversarial review

1. **Sampled evidence.** Which results above are proofs and which are only sampled? My position: gauge-literal equality is proved (shift invariance of exact minimum subtraction) and the sweep is a regression check; the step-7 wrap follows from the `PELL_ORBIT` table lookup in the code, but the claim that tagged components always hold `orbit[step mod 8]` rests on reading where tags are created (`LD` of `(1,0)` and `ROT`), which was not exhaustively verified.
2. **C++ abort.** The evidence that it is a display-path overflow and not an instruction fault: with unbuffered stdout the output reaches the `Quadray Registers` header and then `terminate`; all 10 `QROT` steps completed; instruction faults are caught in `run()` and reported as `Execution rejected` with rc 1 (as at the 14th `QROT`). No debugger backtrace was taken (`gdb` `catch throw` would settle which expression throws).
3. **O6 `MISSING_IN_CLAIMED_PROFILE`.** The test only compares the Python VM table with the assembler table (claim: the assembler header comment) and matrix-row columns; it does not use RTL. The RTL extractor is regex-based (`[63:56] == 8'hXX` and `localparam OP_*`). Verified miss: `hardware/rtl/core/spu13/spu13_surd_exec.v` decodes the `0x70–0x77` extension with `case(op)` over relative indices, so the inventory has no RTL rows for the Surd opcodes. Other `case(opcode)` decoders not inspected: `spu_instr_decode.v`, `spu13_lucas_mac.v`, `spu4_sequencer.v` (SPU-4 is outside the extractor's file list entirely). Also, the shadowed duplicate `POLY_STEP 0x60` in the Python VM dict is counted as VM support although it is not executable.
4. **D1 reachability.** No row of the D1 table is backed by synthesis or elaboration. All are code-reading inferences from `spu13_core.v` parameters, the `spu_a7_top.v` spin-to-parameter `localparam`s, board tops' instantiations and a grep of testbench parameter overrides. Silicon-ledger entries for the spins were not cross-checked against exact parameter sets.

## Limitations

- Opcode extraction is regex-based (see question 3).
- Audits cover in-tree tops and testbenches only; external configurations are not evaluated.
- **SPU-4 `QROT` is a different operation (resolved by independent review, checked at `f61fee0`).** `spu4_sequencer.v:138` decodes `QROT` as `8'h45` (ISA-A: `0x11`; the same arm also starts `QADD` `8'h40`). `spu4_euclidean_alu.v` computes a Q8.8 fixed-point circulant transform of B, C, D with F/G/H coefficients (`B'=F·B+H·C+G·D`, with overflow fold and `henosis_pulse`), A passed separately. The shared mnemonic does not imply shared semantics. The ledger's SPU-4 `QROT` silicon entries (around §3.2j) exercise that circulant ALU with specific fixtures; they are **not** evidence for the ISA-A operation. The O6 inventory is SPU-13/ISA-A only; SPU-4 must be inventoried as its own profile, not merged. Not extended here.
- The SPU-13 core RTL has no `QROT` decode in the O6 inventory; no SPU-13 RTL comparison was made.
- Identities `b063280`, `2cbfa6f`, `19d652a` (and the commit containing this file) are distinct; conclusions apply to the identity stated.
- Nothing here is a silicon claim. The ledger's `QROT` entries concern the SPU-4 implementation; none attests the ISA-A VM semantics characterized here.
